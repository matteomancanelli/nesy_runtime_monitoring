Good question to nail down before you interpret timing numbers, because the whole CPU/GPU split is what's generating the orderings you're seeing.

The architectural difference. A CPU has a handful of cores (say 8–16), each one very fast, with large caches, branch prediction, and out-of-order execution. It's latency-optimised: built to finish a single chain of dependent operations as quickly as possible, and it handles irregular, branchy, sequential code well. A GPU has thousands of tiny cores that are individually slow and dumb. It's throughput-optimised: built to do the same operation on enormous amounts of data at once. The mental model I'd hold onto: the CPU is a sports car and the GPU is a freight train. For one passenger, take the car. For ten thousand passengers going the same way, the train wins easily despite taking longer to get moving.

The GPU's execution model is SIMT — single instruction, multiple threads. Threads run in lockstep groups (warps of 32 on NVIDIA); all 32 execute the same instruction on different data each clock. This is why GPUs love big uniform array math and dislike branchy code: if threads in a warp take different if branches, the hardware has to run both branches and mask, so divergence is expensive. A DFA transition matmul is exactly the uniform workload it wants; a Python loop with per-cell verdict checks is exactly what it doesn't.

What actually happens when you use cuda. Two physically separate memories exist: host RAM (system memory, where CPU tensors live) and device VRAM (on the GPU board, where cuda tensors live). When you call .cuda() or device="cuda", the tensor's bytes are copied across the PCIe bus into VRAM. From then on, each operation on that tensor is launched as a kernel — a little program shipped to the GPU. Three taxes come with this:

Transfer cost — moving data host↔device over PCIe is slow relative to compute. You pay it on the way in and again whenever you bring results back.
Kernel-launch overhead — every operation costs a few microseconds just to tell the GPU "do this now," independent of how much work it is. A matmul on a 4×4 matrix and on a 4000×4000 matrix have nearly the same launch cost; the small one is almost all overhead.
Synchronisation stalls — GPU execution is asynchronous. When you launch kernels, the CPU queues them and moves on without waiting. But the moment you read a value back — .item(), .cpu(), an if on a GPU scalar, a print — the CPU must block until the GPU has actually finished. Do that every cell and you serialise everything, destroying the throughput advantage.
This is the concrete reason I suspected your batch=1 DeepDFA should run on CPU. At batch size 1, each cell is a tiny matmul using a sliver of the thousands of cores, and if you read the verdict each step you also force a sync. You pay all three taxes for almost no parallel work, so the CPU's plain fast arithmetic wins. The GPU only pays off once the per-op work is large enough to amortise the fixed costs.

Implicit or manual? Both — and the split is the key insight. The low-level parallelism is automatic. When you call torch.matmul or bmm on cuda tensors, PyTorch dispatches to NVIDIA's cuBLAS, which spreads the arithmetic across the cores for you. You never write thread code or manage cores. That part is genuinely implicit.

What is not automatic is creating enough parallel work to fill the machine. The GPU can't parallelise something you've expressed as ten thousand tiny sequential operations — it can only parallelise within each operation. So your job is to restructure the computation so that one big operation replaces many small ones. That restructuring is manual and it's exactly what your batch_run does: instead of looping run(trace) over 1000 traces (1000 sequential sets of tiny ops), it stacks all 1000 traces as rows and does one bmm per cell across the whole batch. Now the per-cell operation is large, the cores are busy, and the launch/transfer overhead is divided across 1000 traces. That's the regime where the freight train beats the sports car — and it's why Exp 3 (batch-size axis) is the figure that's supposed to show DeepDFA pulling ahead, while Exp 1 (batch=1) is not.

Two corollaries that bear directly on your numbers. First, the manual side also means keep data on-device and don't sync per cell — encode the whole batch to cuda once, run all cells, read verdicts back at the end, not each step. A per-cell .item() will make even a well-batched DeepDFA look terrible. Second, this is exactly why RuleRunner stays bottlenecked even when batched: its depth+1 convergence passes per cell are dependent — each pass needs the previous one's result — so you can't collapse them into one kernel. You get cross-trace batching (the rows) but you still launch depth+1 sequential kernels per cell, each with its own launch and dependency. DeepDFA launches one. That surviving within-step sequential dependency, not the trace count, is the real architectural difference your Exp 2 and Exp 3 are trying to expose.

So when you read your CSVs: low batch favours CPU and favours symbolic; the GPU's advantage is something you engineer into existence by batching and by not syncing, and it should appear as the batch axis grows. Want me to sketch what the three Exp 3 curves should look like as batch size scales (where each crosses over), so you have an expected shape to check your real numbers against?
